# Future server database migration and reconciliation

No paid cloud service or remote database is implemented in 0.5.0. Business services use JDBC repositories and transaction boundaries; BackupFiles contains SQLite-specific snapshot/restore behavior. Replace those infrastructure operations when introducing a server database.

1. Freeze writes and create a verified SQLite backup plus Business controls → Backup and restore → Export database JSON. Preserve the original backup, SHA-256 manifest and export securely; both include account hashes and customer data.
2. Create a PostgreSQL schema using versioned server migrations. Map SQLite INTEGER money to BIGINT paise, quantities to integer/bigint, text IDs to UUID or stable text as appropriate (initial category IDs are text), ISO timestamps to TIMESTAMPTZ and effective dates to DATE. Keep case-insensitive unique SKU/username/category behavior explicitly; preserve all unique request keys, invoice numbers, FK links and indexes. Do not execute SQLite PRAGMA/VACUUM statements against PostgreSQL or copy SQLite schema_migrations hashes as server migrations.
3. Validate format eastoftown-portable-v1 and the expected table/column allowlist. Load categories/users/settings, products/variants/taxes, customers, imports, invoices/items/payments/checkout requests, stock adjustments/movements, returns/items/refunds, expense categories/expenses, customer changes and audit rows in FK dependency order. Use prepared batch inserts and one controlled transaction; never concatenate values into SQL. Preserve all original IDs, barcode strings, item snapshots, costs, request hashes, actor references, timestamps and saved sequence. Do not re-generate identifiers or invoice numbers. Test the import against a disposable server database first.
4. Reconcile every source/target table count and stable sorted row hashes with normalized timestamp/numeric representations. Compare invoice subtotal/discount/tax/total sums, payment/refund totals by method, per-variant stock movement sums (no negative stock), customer net purchases, historical profit cost coverage and active expense totals by month. Check zero FK orphans and duplicate SKUs/barcodes/invoice numbers/request keys. Re-run checkout/retry, partial/final return, cancellation and backup acceptance tests on the target.
5. Introduce server writer locking/serializable safeguards so concurrent branch checkouts cannot oversell or reuse invoice sequences. Multi-branch ownership and numbering require a separate approved design. Invalidate old sessions at cutover, preserve BCrypt hashes and recovery hashes and restrict network access using authenticated encrypted connections.
6. Keep SQLite and server reconciliation evidence and rollback backups. Only cut over after review and successful reconciliation. Stop target writes before any rollback; do not silently combine divergent ledgers. Document the chosen hosting, access and backup policy before deployment.

The export endpoint is the current portable migration utility; it deliberately does not guess credentials, create a cloud account or automatically write into a server database.
